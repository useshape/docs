Bookmarks let you pin specific lines in your codebase and return to them instantly, even after closing and reopening Shape. They're ideal for marking failing tests, sections you plan to refactor, or any spot you know you'll need to revisit.

## Toggle a Bookmark

Place your cursor on the line you want to bookmark, then press `Ctrl+Alt+B`. A bookmark icon appears in the editor gutter. Press `Ctrl+Alt+B` again on the same line to remove it.

<Note>
There is no activity bar icon for Bookmarks. All bookmark actions are available through keyboard shortcuts or the Command Palette.
</Note>

## Navigate Between Bookmarks

| Action | Shortcut |
|---|---|
| Jump to next bookmark | `Ctrl+F2` |
| Jump to previous bookmark | `Shift+F2` |

Navigation wraps around — after the last bookmark, the next press takes you back to the first. Bookmarks in other files open those files automatically.

## View All Bookmarks

Open the Command Palette (`Ctrl+Shift+P`) and run **Bookmarks**. The list shows each bookmark's file path, line number, and label. Click any entry to jump to it, or remove individual bookmarks from this view.

## Bookmark Labels

Each bookmark gets a default label of **Line N** (where N is the line number). When the cursor is on a word at the time you set the bookmark, Shape may use that word as the label instead, making your bookmarks easier to identify at a glance.

## Where Bookmarks Are Stored

Bookmarks are stored locally, tied to the workspace path on your machine. They:

- **Persist across sessions** — survive closing and reopening Shape
- **Are not committed to Git** — they don't appear in your repository
- **Are not synced to your Shape account** — they stay on this device

## Tips for Using Bookmarks Effectively

<Tip>
Combine Bookmarks with the Outline sidebar for two levels of navigation: use the Outline to jump between functions and classes within a file, and use Bookmarks to track key lines across multiple files.
</Tip>

Common bookmark use cases:

- **Failing tests** — bookmark the assertion line while you hunt for the root cause
- **TODO comments** — mark spots that need work before a PR is merged
- **Refactor targets** — track every call site you need to update during a rename
- **Cross-file context** — hold your place in file A while you read related code in file B
